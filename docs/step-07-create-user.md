# Step 07 — Create User

## Scope

Implement the first Users application use case: create a user through the domain repository boundary without exposing Prisma or the database primary key to the application response.

## Implemented

- Added `CreateUserDto` with validation and normalization for username, email, and phone.
- Requires at least one user identity field: username, email, or phone.
- UUID is generated by the `User` domain entity; callers cannot supply or override it.
- Creation uses domain defaults: `pending`, active, and unverified.
- Username, email, and phone uniqueness is checked before persistence.
- Database unique-constraint races are mapped to a domain/application conflict error instead of leaking Prisma errors.
- Persistence runs through `UserRepository`; the Prisma adapter uses the existing transaction boundary.
- Create response contains only the public user fields and never exposes the database `id`.
- Added unit coverage for successful creation, normalization, invalid input, duplicate username/email/phone, and response safety.

## Acceptance Criteria

- A user can be created through an application service.
- UUID is generated automatically.
- Username/email/phone uniqueness is enforced both preflight and at the database constraint boundary.
- Persistence is transaction-aware and isolated behind `UserRepository`.
- Invalid create input produces a deterministic validation error.
- Database/Prisma errors are not leaked for unique conflicts.
- The create response does not expose the internal bigint database identifier.
